# Litoreya — план проекта

Веб-приложение для хранения зашифрованных постов (текст, пароль) с end-to-end шифрованием
на стороне клиента.

---

## 1. Ключевые архитектурные решения

| Решение | Выбор | Почему |
|---|---|---|
| Фронтенд | Next.js в режиме `output: 'export'` (статический экспорт) | На shared хостинге нет Node. SSR/Server Actions/API routes недоступны. Для E2E-шифрования это не потеря: сервер всё равно не может отрендерить содержимое — оно зашифровано. |
| Бэкенд | Laravel как чистое JSON API | Никаких Blade-вью. Сервер — хранилище непрозрачных блобов + аутентификация. |
| Аутентификация | Laravel Sanctum, cookie-режим (SPA) на одном домене | HttpOnly-кука не крадётся через XSS, в отличие от токена в localStorage. Переход на Bearer-токены оставить возможным (абстракция в HTTP-клиенте) — понадобится, если фронт уедет на другой домен. |
| БД | MySQL 8 | Требование. Сервер не индексирует содержимое, поэтому от БД нужны только реляционные связи. |
| Локальная разработка | Docker, **Apache + mod_php** (не nginx+fpm) | Паритет с shared хостингом. Логика `.htaccess` должна проверяться локально, иначе она сломается только на проде. |

### Главное ограничение, определяющее почти всё

Приложение должно запуститься на shared хостинге — «просто файлы PHP под Apache».
Из этого следует: нет Node в проде, нет гарантии SSH/Composer/artisan, нет постоянных
процессов (очереди, воркеры, WebSocket). Всё, что нельзя выполнить на хостинге, должно
выполняться на этапе сборки и заливаться готовым.

## 2. Криптографическая модель

Это ядро проекта. Ошибка здесь не чинится патчем — она чинится ре-шифрованием всех данных
всех пользователей.

> Подробный разбор схемы ключей, операций, реализации на WebCrypto и ограничений —
> в [crypto-design.md](./crypto-design.md).

### 2.1 Два секрета с разными ролями

- **Пароль** — доказывает серверу, кто ты. Уходит на сервер по HTTPS, хранится как хеш
  (стандартный `Hash::make`, bcrypt/argon2id).
- **Ключевая фраза** — расшифровывает данные. **Никогда не покидает браузер.** Сервер
  не должен иметь возможности расшифровать посты даже при полном доступе к БД.

### 2.2 Схема ключей: обёрнутый мастер-ключ (wrapped DEK)

Не выводить ключ шифрования постов напрямую из ключевой фразы. Вместо этого:

```
keyphrase ──PBKDF2(salt, 600k, SHA-256)──> KEK  (key-encryption key)
DEK = random(32 байта)                          (data-encryption key, мастер-ключ данных)
wrapped_dek = AES-GCM(KEK, iv, DEK)             (то, что лежит на сервере)
verifier    = AES-GCM(DEK, iv, "litoreya-v1")   (канарейка для проверки фразы)
```

Посты шифруются **DEK'ом**, а не KEK'ом. Выгода:

- **Смена ключевой фразы** = перешифровать 32 байта (`wrapped_dek`), а не все посты.
- **Recovery-код** реализуется бесплатно: генерируем второй случайный код, выводим из него
  KEK₂ и кладём второй `wrapped_dek`. Пользователь печатает код один раз при регистрации.
- **Проверка фразы офлайн**: клиент разворачивает DEK и расшифровывает `verifier`. Сошлось —
  фраза верна. Не сошлось — ошибка показывается локально, на сервер ничего не уходит.

Всё через **WebCrypto API** (`crypto.subtle`) — он есть в браузере, не требует библиотек и
работает с неизвлекаемыми ключами. Argon2id (через WASM) — возможное улучшение позже, PBKDF2
с высоким числом итераций достаточен для старта.

### 2.3 Шифрование поста

```
iv         = random(12 байт)                    // уникальный на каждое сохранение
plaintext  = JSON({ title, body, поля по типу }) // заголовок ТОЖЕ внутри
ciphertext = AES-GCM(DEK, iv, plaintext)
```

На сервер уходит: `type`, `category_id`, `iv`, `ciphertext`, `payload_version`.
Сервер не видит ни заголовка, ни содержимого, ни длины осмысленных полей.

**`payload_version` обязателен.** Формат JSON внутри шифротекста будет меняться, а мигрировать
его умеет только клиент — серверная миграция не может тронуть содержимое поста. Версия
позволяет расшифровывать старый формат и лениво переписывать в новый.

### 2.4 Категории и поиск

Названия категорий тоже шифруются; в открытом виде остаётся только `id`. Клиент грузит список
категорий и расшифровывает его.

**Структура дерева (`parent_id`) остаётся открытой, и это осознанно.** Сервер видит форму
дерева — сколько веток и какой они глубины, — но не названия: они внутри `ciphertext`.
Спрятать `parent_id` в шифротекст значило бы отказаться от внешнего ключа и от серверной
проверки принадлежности родителя тому же пользователю, то есть выменять реальную гарантию
целостности на сокрытие метаданных, которые и так следуют из `position` и `posts.category_id`.

**Поиск в MVP — только на клиенте**, после расшифровки. Серверный поиск по зашифрованным данным
требует blind index (`HMAC(DEK, нормализованное_слово)`) — это реально, но добавляет утечку
частотности и усложняет запись. Вне MVP.

### 2.5 Хранение ключа в браузере — где я предлагаю отойти от ТЗ

Ключевая фраза в `localStorage` в открытом виде означает: одна XSS — и злоумышленник забирает
саму фразу, то есть доступ **навсегда**, даже после смены пароля и разлогина.

Предлагаю:

- Спрятать хранилище за интерфейсом `KeyVault` (`unlock()`, `getKey()`, `lock()`) с двумя
  реализациями. Тогда смена стратегии — это одна строка, а не переписывание.
- Реализация по умолчанию: держать **DEK как non-extractable `CryptoKey` в IndexedDB**.
  JS физически не может прочитать такой ключ — только использовать. XSS сможет расшифровать
  данные, пока сессия жива, но не украдёт фразу и не унесёт ключ на свой сервер.
- Добавить auto-lock по бездействию (например, 15 минут) и явную кнопку «Заблокировать».

Начать можно с простой `localStorage`-реализации, чтобы не тормозить MVP, — но интерфейс
завести сразу.

### 2.6 Забытая ключевая фраза = данные потеряны

Восстановления нет и не может быть — это следствие того, что схема работает как задумано.
Поэтому в UI регистрации нужны: явное предупреждение с подтверждением и обязательная выдача
recovery-кода (см. 2.2).

## 3. Схема БД

```
users
  id, name, email, password              -- стандартный Laravel
  kdf_algo, kdf_salt, kdf_iterations     -- параметры вывода KEK
  wrapped_dek, wrapped_dek_iv            -- мастер-ключ, обёрнутый ключевой фразой
  recovery_dek, recovery_dek_iv          -- он же, обёрнутый recovery-кодом (nullable)
  verifier, verifier_iv                  -- канарейка проверки фразы
  timestamps

categories
  id, user_id, iv, ciphertext            -- имя категории зашифровано
  parent_id (nullable, self-FK)          -- дерево; открыто, см. 2.4
  position, timestamps

posts
  id, user_id, category_id (nullable)
  type enum('text','password')           -- открыто: нужно для иконки/раскладки формы
  iv, ciphertext, payload_version
  timestamps, deleted_at (soft delete)   -- deleted_at нужен для синка PWA
```

Бинарные поля — `VARBINARY`/`BLOB` либо base64 в `TEXT`. Base64 проще в отладке и в JSON API;
overhead ~33% приемлем на таких объёмах.

Индекс `posts(user_id, updated_at)` — под инкрементальный синк офлайн-режима.

## 4. API

```
POST   /api/auth/register    {name, email, password, crypto:{...конверт...}}
POST   /api/auth/login       {email, password} → user + crypto-конверт
POST   /api/auth/logout
GET    /api/me
PUT    /api/auth/keyphrase   {новый конверт}      -- только rewrap, посты не трогаются

GET    /api/categories                 POST /api/categories
PUT    /api/categories/{id}            DELETE /api/categories/{id}

GET    /api/posts?category_id=&updated_since=
POST   /api/posts                      GET /api/posts/{id}
PUT    /api/posts/{id}                 DELETE /api/posts/{id}
```

Валидация на сервере — только структурная: корректный base64, лимиты размера, владелец записи.
Содержимое для сервера непрозрачно, и это проверяемое свойство: в тестах убедиться, что ни один
эндпоинт не принимает и не возвращает открытый текст поста.

Rate limiting на `/api/auth/login` и `/api/auth/register` — обязательно.

## 5. Раскладка на shared хостинге

Папка домена — симлинк на `public/` текущего релиза. Код приложения лежит вне веб-корня,
наружу открыт только `public/`.

```
<домашний каталог>/
    <папка-домена>  -> litoreya/current/public   ← создаётся вручную один раз
    litoreya/
        current     -> releases/<ts>             ← переключается атомарно
        releases/<ts>/{app,config,vendor,...,public/}
        shared/{.env, storage/, backups/}
```

Статический экспорт Next.js кладётся в тот же `public/`, рядом с `index.php`; разводит их
`backend/public/.htaccess` — единственный `.htaccess` проекта, он же используется в dev и
prod-like.

### Почему именно так

Front controller оказывается в корне DocumentRoot, поэтому Symfony получает пустой `baseUrl`
и полный `pathInfo` — маршрут `/api/health` находится сам. Прежняя раскладка держала
front controller в подкаталоге `/api/` и требовала подмены `SCRIPT_NAME`; это было
единственное место, где прод структурно отличался от dev.

### Что делается на сборке, а что на сервере

| Шаг | Где | Почему |
|---|---|---|
| `npm ci` + `next build` | сборка | воспроизводимость |
| `composer install --no-dev` | сборка, **внутри релиза** | в `backend/` вырезал бы dev-зависимости из рабочего дерева |
| `package:discover` | сборка | `packages.php` не содержит абсолютных путей, везти безопасно |
| `config:cache`, `route:cache` | **сервер** | в `config.php` запекаются абсолютные пути и `APP_KEY`; локальный кеш даёт 500 без записи в лог |
| `migrate` | сервер, до переключения | схема должна быть готова к моменту, когда домен посмотрит на новый код |

### Ограничения хостинга и обходы

| Проблема | Решение |
|---|---|
| Нет Node в проде | статический экспорт, `output: 'export'` |
| `php` в PATH может быть другой версии | `DEPLOY_PHP` в `.env`, проверять `which -a php php8.2` |
| Панель может пересоздать папку домена | смотреть её содержимое до удаления: там может быть `.htaccess` с директивой выбора версии PHP |
| Нет воркеров | `QUEUE_CONNECTION=sync`: при `database` любой `dispatch()` тихо лёг бы в таблицу навсегда |

## 6. Локальное окружение (Docker)

Сервисы: `apache-php` (образ на базе `php:8.3-apache`), `mysql:8`, `node` (dev-сервер Next),
опционально `phpmyadmin`, `mailpit`.

Два режима запуска — оба нужны:

1. **dev** — Next dev-сервер на `:3000` с проксированием `/api` в Apache. Быстрый HMR.
2. **prod-like** — статика собрана `next build` и разложена ровно как на хостинге, всё
   раздаёт тот же Apache. Это единственный способ отловить проблемы `.htaccess`, путей
   и SPA-fallback **до** деплоя, а не после.

## 7. Этапы

### Фаза 0 — Каркас ✅ выполнено

Docker-сборка (php:8.2-apache + MySQL 8 + Node 20), Laravel 12, Next.js 16 со статическим
экспортом, health-check, оба режима запуска.

Что вскрылось при проверке prod-like режима и учтено в коде:

- front controller в подкаталоге `/api/` заставлял Symfony считать путь как `health`
  вместо `api/health` — исправлено подменой `SCRIPT_NAME` в `hosting/public_html/api/index.php`;
- Apache не мог понизить привилегии до числового uid (`getpwuid` не находит имя) и работал
  под root — uid `www-data` сдвигается к пользователю хоста при сборке образа;
- `trailingSlash: true` добавлял 308-редирект на `/api/*` в dev, чего нет в проде —
  в dev включён `skipTrailingSlashRedirect`;
- `Referrer-Policy: no-referrer` сломал бы cookie-режим Sanctum — заменён на `same-origin`;
- тесты переведены с SQLite на MySQL.

### Фазы 1–2 — Аутентификация и крипто-ядро ✅ выполнено

Объединены намеренно: схема ключей определяет форму таблицы `users`, и создавать её дважды
незачем. Конверт формируется атомарно при регистрации, крипто-колонки сразу `NOT NULL`.

Бэкенд: Sanctum в cookie-режиме, `POST /api/auth/register|login|logout`, `GET /api/auth/me`,
`PUT /api/auth/keyphrase`, троттлинг по IP и по паре «email + IP», валидация конверта по
точным размерам после декодирования base64, нижняя граница итераций KDF.

Фронтенд: `lib/crypto.ts` (WebCrypto), `lib/keyvault.ts` (неизвлекаемый ключ в IndexedDB
с auto-lock), экраны входа/регистрации, выдачи recovery-кода и разблокировки.

Тесты: 25 серверных, 30 на крипто-ядро и KeyVault, 4 интеграционных на стык клиентского
модуля с живым API.

Что вскрылось и учтено:

- Sanctum включает сессию только для запросов с `Referer`/`Origin` из списка stateful-доменов;
  без них — `Session store not set on request`. Тесты проставляют `Origin`, как браузер;
- `/sanctum/csrf-cookie` лежал вне `/api` и на хостинге ушёл бы в SPA-fallback — префикс
  Sanctum переопределён на `api`;
- `bin/build-release.sh` делал `rm -rf` каталога, примонтированного в контейнер prod-like:
  inode уничтожался, bind-mount повисал, Apache отдавал 404. Теперь чистится содержимое;
- `assertGuest()` без аргумента читает кеш `RequestGuard`, а не состояние сессии, потому что
  `auth:sanctum` делает guard `sanctum` дефолтным.

### Фаза 2а — что осталось от крипто-ядра

- генератор diceware-фразы на экране регистрации (сейчас фраза вводится вручную);
- ~~экран смены ключевой фразы в UI~~ — сделано в фазе 4б, на странице профиля.

### Фаза 3 — Посты и категории ✅ выполнено

Таблицы `posts` и `categories`, CRUD API, дашборд с категориями, поиском и редактором.
Типы записей: пароль и заметка. Для пароля — скрытие значения, копирование с очисткой буфера
через 30 с, встроенный генератор.

Проверено не только через API, но и прямым запросом в БД: открытого текста в `ciphertext`
не встречается, включая заголовки и названия категорий.

Решения, зафиксированные тестами:

- **чужие записи дают 404, а не 403** — иначе код ответа сам подсказывал бы, какие id
  существуют;
- **удаление категории не удаляет записи** — они теряют категорию (`nullOnDelete`).
  Каскад был бы разрушительным: восстановить нельзя, а показать «вы уверены, там вот это»
  сервер не может, он не видит содержимого;
- **`payload_version` из будущего отвергается** — иначе запись приняли бы молча, а
  расшифровать её потом не смог бы никто;
- **нечитаемая запись не роняет дашборд** — помечается и показывается, остальные работают;
- **пароль не попадает ни в превью списка, ни в поиск.**

### Фаза 4 — Деплой на shared хостинг ✅ инструменты готовы, деплой не выполнен

Раскладка перестроена под симлинки (см. §5), собран инструментарий: `make release`,
`make deploy`, `make rollback`, `make smoke`. Prod-like воспроизводит дерево релизов
целиком, включая оба симлинка.

Что вскрылось при перестройке:

- `DirectoryIndex` жил в vhost, а не в `.htaccess` — на хостинге vhost не наш, и корень
  сайта отдал бы JSON-404 вместо SPA;
- стоковый ларавелевский 301, срезающий хвостовой слеш, конфликтует с `trailingSlash: true`
  и ломал бы `POST /api/posts/`;
- opcache в локальном образе был выключен — главный риск симлинковой схемы не
  воспроизводился;
- первая версия сборки запускала `composer install --no-dev` в `backend/`, вырезая
  dev-зависимости из рабочего дерева;
- дым-тест проверял коды ответа, а при SPA-fallback отсутствующий путь честно отдаёт 200 —
  проверка показывала утечку там, где её нет. Теперь сверяется содержимое.

Осталось выполнить на хостинге: разведка папки домена, создание БД и `shared/.env`,
первый деплой, дым-тест. Пошагово — в плане деплоя.

### Фаза 4а — доработки интерфейса

Две доработки, не меняющие крипто-модель.

**Показ пароля по кнопке-глазику на всех секретных полях.** Сейчас переключатель есть ровно
в одном месте — в поле пароля внутри записи, и он текстовый. Пять остальных полей (пароль
при входе, пароль и ключевая фраза с повтором при регистрации, фраза при разблокировке) не
дают проверить набранное. Для ключевой фразы это не косметика: опечатка при регистрации
запирает пользователя навсегда — recovery-код выдаётся уже после, а восстановления нет
по построению (см. 2.6). Поле «повтор фразы» ловит расхождение, но не показывает, что
именно введено.

Реализация: один переиспользуемый `SecretInput` вместо шести самописных полей, иконка —
инлайновый SVG. Библиотеку иконок не подключать: в зависимостях фронта сейчас только
`next`/`react`/`react-dom`, и тянуть пакет ради двух глифов несоразмерно.

**Категории — дерево.** Добавляется `parent_id`, меню выводится вложенно, ветки
сворачиваются. Принятые решения:

| Вопрос | Решение | Почему так |
|---|---|---|
| Удаление категории с детьми | дети поднимаются на уровень выше | продолжение уже принятого правила «удаление категории не разрушает то, что пользователь не удалял»: записи теряют категорию, но не исчезают — ветка ведёт себя так же |
| Клик по родительской категории | показывает записи всей ветки | иначе родительские узлы выглядят пустыми, хотя под ними есть записи |
| Глубина | не больше 5 уровней | защита от циклов обязательна в любом случае; лимит глубины дополнительно страхует от дерева, которое не помещается в боковую панель шириной 14rem |

Цикл (перенос категории в собственного потомка) и чужой родитель отвергаются сервером
с 422 — по тому же образцу, по которому `PostRequest` уже проверяет `category_id`.
Предел глубины продублирован на клиенте и сервере и обязан совпадать.

Логика дерева выносится в отдельный чистый модуль `frontend/lib/tree.ts`: компонентных
тестов в проекте нет (`vitest` запущен в `node`-окружении и собирает только `lib/**`),
и это единственный способ покрыть построение дерева, сирот, циклы и свёрнутые ветки
автоматическим тестом, а не глазами.

Состояние развёрнутых веток — первое обращение проекта к `localStorage`. От него
сознательно отказались для мастер-ключа (см. 2.5); здесь хранится только список
развёрнутых узлов, и запрет не ослабляется.

Миграция аддитивная: старый код колонку игнорирует, поэтому откат релиза безопасен.

### Фаза 4б — Профиль и управление доступом ✅ выполнено

Страница `/profile/` с вкладками «Аккаунт» и «Безопасность». На второй — смена пароля
и смена ключевой фразы. Это закрывает пункт фазы 2а и добавляет смену пароля, которой
не было вовсе: эндпоинта не существовало.

**Появился второй маршрут** — первый случай в проекте. Развилка по состоянию сессии
вынесена из `app/page.tsx` в `SessionGate` и обязана стоять на каждом маршруте: по прямой
ссылке на внутреннюю страницу приходит кто угодно в любом состоянии. Незалогиненного
на внутренней странице уводим на главную, а не показываем форму входа, — открывать там
всё равно нечего.

Раскладка выдержала маршрут без правок: `trailingSlash: true` даёт `out/profile/index.html`,
блок «существующие файлы и каталоги» в `.htaccess` отдаёт каталог напрямую, редирект
`/profile` → `/profile/` делает mod_dir.

Принятые решения:

| Вопрос | Решение | Почему так |
|---|---|---|
| Ввод старой фразы при смене | обязателен | не UX-выбор: ключ в `KeyVault` неизвлекаемый, `wrapKey` на таком бросает `InvalidAccessError` (crypto-design §5.2). Обойти можно только извлекаемой копией DEK в памяти — ровно та угроза, от которой защищает неизвлекаемый ключ |
| Другие сессии при смене пароля | завершаются сразу | смысл смены при утечке в том, чтобы выгнать вошедшего. Удаляем строки `sessions` напрямую, а не через `logoutOtherDevices()`: тот убивает сессию не в момент смены, а когда её владелец что-то сделает |
| Recovery-код при смене фразы | остаётся прежним | обёртка recovery независима от фразы. На форме об этом сказано прямо — иначе пользователь решит, что старый код умер |

**Троттлинг расширен.** Лимитер `auth` ключуется по полю `email`, которого у
авторизованного запроса нет: навесить его на `/auth/password` значило бы свалить всех
пользователей за одним NAT в общий счётчик. Заведён `sensitive` с ключом по id
пользователя, и повешен на оба эндпоинта, подтверждаемых паролем, — смена фразы до этого
не была защищена от перебора вовсе.

### Фаза 5 — PWA ✅ выполнено

Манифест, service worker, офлайн-доступ: зашифрованные блобы кешируются в IndexedDB,
расшифровка на лету. Инкрементальный синк через `updated_since` + `deleted_at`.

**Офлайн — только чтение.** Записи и категории открываются без сети, изменяющие действия
блокируются с объяснением. Очередь отложенных правок не делалась намеренно: она требует
стратегии конфликтов и обработки отказов сервера уже после того, как пользователь ушёл, —
это отдельная задача, а не довесок к офлайн-чтению.

**Service worker написан руками, без Serwist** — отход от исходной записи в этом плане.
Интеграции такого рода цепляются к бандлеру Next, а проект уже обжигался на том, что
версия ведёт себя не так, как ожидалось. Задача узкая — оболочка и хешированные ассеты,
без API, — и уложилась в сотню строк без единой зависимости.

Решения, которые стоит помнить:

| Вопрос | Решение | Почему так |
|---|---|---|
| Данные в Cache API | нет, только IndexedDB | шифротекст в двух местах с разными правилами устаревания разъедется; к тому же отданный из кеша ответ API после разлогина выглядел бы как живая сессия |
| Навигация | сначала сеть, кеш в запасе | обратный порядок отдал бы старую разметку со ссылками на чанки, которых в новом релизе нет, — тот самый `ChunkLoadError` |
| Обновление версии | по кнопке, не `skipWaiting` | перезагрузка посреди редактирования потеряла бы набранное, а черновиков в приложении нет |
| Отметка синхронизации | `updated_at` с сервера | собственные часы браузера разошлись бы с хостингом, и часть изменений пропускалась бы молча |
| Категории | заменяются целиком | у них нет ни soft delete, ни `updated_since`: узнать об удалённой иначе нельзя |

**Отметка релиза подставляется в `sw.js` при сборке.** Браузер сравнивает воркер побайтово:
без подстановки файл не менялся бы от релиза к релизу, обновление оболочки не приехало бы
никогда. Сборка и дым-тест проверяют, что плейсхолдер заменён.

Кеш переживает блокировку, но стирается при выходе из аккаунта: прочитать его без ключа
нельзя, а вот оставлять чужие блобы в браузере после выхода незачем.

Соединение с IndexedDB вынесено в `lib/idb.ts`. База одна, хранилищ стало несколько, и
открывать её из разных модулей с разными номерами версий нельзя — второй получил бы
`VersionError` либо заблокировал первого.

### Фаза 5а — Корзина

Сейчас `posts.deleted_at` уже проставляется, но существует только ради синка: удалённая
запись исчезает из интерфейса безвозвратно, хотя строка остаётся в таблице. Восстановить её
можно единственным способом — запросом в базу руками.

Идёт **после PWA намеренно**: восстановление заставляет запись *появиться* снова, а это
тот же самый контракт синка, что и её исчезновение. Делать корзину раньше — значит потом
переписывать её под инкрементальный обмен.

Объём:

- `GET /api/posts?trashed=1` — содержимое корзины;
- восстановление и окончательное удаление отдельными маршрутами (ссылки на методы
  контроллера, не замыкания — `route:cache` собирается при каждом деплое);
- запросы строятся от `$request->user()->posts()->withTrashed()`, принадлежность
  по-прежнему обеспечивается формой запроса;
- в интерфейсе — экран корзины, восстановление записи и «очистить корзину».

Решения, которые стоит принять до кода:

**Только записи, не категории.** Удаление категории уже не разрушает данные: записи
остаются, подкатегории поднимаются уровнем выше. Безвозвратно теряется только удалённая
запись — корзина нужна ровно там.

**Автоочистки по расписанию не будет.** На shared хостинге нет ни воркеров, ни гарантии
cron (`QUEUE_CONNECTION=sync` выбран по этой же причине). Срок хранения, который тихо не
соблюдается, хуже отсутствия срока: пользователь считает, что запись удалена окончательно,
а она лежит. Поэтому очистка — явное действие, и только оно.

**Восстановление не возвращает категорию.** Если категорию удалили, пока запись лежала
в корзине, `category_id` уже обнулён внешним ключом — запись вернётся «без категории».
Сервер не может предложить иного: он не видит ни названий категорий, ни содержимого записи.

**Окончательное удаление подтверждается явно.** Это единственная необратимая операция
в приложении, и сервер не в состоянии показать, что именно исчезнет, — для него это
шифротекст. Значит, предупреждение обязано быть на клиенте, где запись расшифрована.

Крипто-модель не затрагивается: в корзине лежит тот же шифротекст.

## 8. Риски

- **Забытая ключевая фраза** — данные не восстановить. Митигация: recovery-код + предупреждение.
- **XSS = полная компрометация** — CSP без `unsafe-inline`, неизвлекаемые ключи, auto-lock.
- **Статический экспорт Next** — легко случайно завязаться на SSR-функциональность. Проверять
  `next build` в CI с самого начала, а не в фазе 4.
- **Shared хостинг** — старый PHP, отсутствие SSH, запрет `.htaccess`. Проверить заранее.
- **Изменение формата payload** — решается `payload_version` с самого первого поста.

## 9. Принятые решения

**Шаринг постов между пользователями — вне области проекта, добавляется при необходимости
позже.** Схема с обёрнутым DEK и `payload_version` делает это аддитивной фичей: посты
переводятся на per-post ключ по одному в момент шаринга, массовой перешифровки не требуется.
Подробности и единственная деталь, требующая клиентской миграции, — в
[crypto-design.md §6](./crypto-design.md).

---

**Один домен для фронта и бэка.** Значит Sanctum в cookie-режиме (HttpOnly, SameSite=Lax),
CORS не нужен. HTTP-клиент на фронте всё равно изолируется, чтобы переход на Bearer оставался
возможен.

**На хостинге есть SSH, PHP 8.2, разрешён `.htaccess`.** Существенно упрощает фазу 4: миграции
накатываются обычным `php artisan migrate`, роут-мигратор и импорт дампов через phpMyAdmin
не нужны. Composer можно запускать на месте, но `vendor/` всё равно собирается в CI —
воспроизводимость сборки важнее удобства.

**Целевая версия PHP — 8.2** (не 8.3). Локальный Docker-образ обязан быть `php:8.2-apache`:
паритет сред теряет смысл, если версии расходятся.
