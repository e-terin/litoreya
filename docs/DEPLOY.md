# Деплой на shared хостинг

Раскладка: папка домена — симлинк на `public/` текущего релиза. Код приложения лежит вне
веб-корня, наружу открыт только `public/`. Обоснование решений — в [PLAN.md §5](./PLAN.md).

```
~/ домашний каталог
    <папка-домена>  -> litoreya/current/public
    litoreya/
        current     -> releases/<ts>          переключается атомарно
        releases/<ts>/                        иммутабельны, хранится 5 штук
        shared/
            .env                              единственный файл с секретами
            storage/                          логи, кеш, общий между релизами
            backups/                          дампы БД перед миграциями
```

Локально та же структура воспроизводится в `deploy/` командой `make prodlike`, где роль
папки домена играет `deploy/webroot`.

---

## Часть 0. Проверки до начала

Выполнить один раз. Каждая проверка закрывает отказ, который иначе проявится не сразу.

### 0.1 Версия PHP — CLI и веб отдельно

Это разные вещи, нужны обе не ниже 8.2: Laravel 12 требует `^8.2` и на 8.1 не запустится.

```bash
ls -1 /opt/php/                       # какие версии установлены
/opt/php/8.2/bin/php -v               # CLI — им работают artisan и composer
```

Версия, под которой реально работает сайт:

```bash
echo '<?php echo PHP_VERSION;' > ~/<папка-домена>/v.php
curl https://<домен>/v.php && rm ~/<папка-домена>/v.php
```

### 0.2 Расширения PHP

```bash
/opt/php/8.2/bin/php -m
```

Обязательны: `ctype`, `dom`, `fileinfo`, `filter`, `hash`, `iconv`, `json`, `libxml`,
`mbstring`, `openssl`, `pcre`, `session`, `tokenizer` — и **`pdo_mysql`**, без которого
не будет подключения к базе (composer его не требует, потому что драйвер выбирается
конфигурацией).

### 0.3 Содержимое папки домена — до того, как её трогать

```bash
ls -la ~/<папка-домена>/
cat ~/<папка-домена>/.htaccess 2>/dev/null
```

**Если версия PHP задаётся директивой в этом `.htaccess`** (`AddHandler`/`SetHandler`) —
при замене папки на симлинк директива исчезнет, и сайт молча уедет на серверный PHP по
умолчанию. Симптом будет выглядеть как синтаксическая ошибка в коде. Строку нужно перенести
в `backend/public/.htaccess` до первого деплоя.

Заодно: **посмотрите в панели, есть ли поле «корень сайта»**. Если есть — укажите в нём
`litoreya/current/public`, и симлинк папки домена не нужен вовсе. Так надёжнее: панель
не будет пересоздавать каталог.

### 0.4 Права `.htaccess`

`.htaccess` должен быть разрешён (`AllowOverride All`) и `mod_rewrite` включён. Косвенная
проверка — что текущий сайт вообще работает с `.htaccess`.

## Часть 1. Первичная выкладка

Делается один раз.

### 1.1 Каталоги

```bash
ssh <пользователь>@<хост>

mkdir -p ~/litoreya/releases
mkdir -p ~/litoreya/shared/storage/framework/{cache,sessions,views}
mkdir -p ~/litoreya/shared/storage/{logs,app}
mkdir -p ~/litoreya/shared/backups
```

`shared/` создаётся до первого релиза: симлинк `.env` внутри релиза должен разрешаться,
иначе `artisan` не запустится.

### 1.2 База данных

Создать в панели хостинга базу и пользователя. Кодировка — `utf8mb4`, сравнение
`utf8mb4_unicode_ci`: посты хранятся base64-строками, но заголовки категорий и служебные
поля должны корректно работать с кириллицей.

Записать четыре значения — они понадобятся в 1.3:

| Параметр | Откуда |
|---|---|
| `DB_DATABASE` | имя базы из панели |
| `DB_USERNAME` | пользователь базы |
| `DB_PASSWORD` | его пароль |
| `DB_HOST` | обычно `localhost`; если панель указывает отдельный хост — взять оттуда |

### 1.3 Файл окружения

```bash
cp <шаблон hosting/env.production.example> ~/litoreya/shared/.env
nano ~/litoreya/shared/.env
```

Заполнить:

- `APP_URL` — базовый адрес со схемой, например `https://example.com`
- `SANCTUM_STATEFUL_DOMAINS` — домены через запятую, без схемы; вариант с `www` перечислить
  тоже, даже если настроен редирект
- `DB_*` — значения из 1.2
- `APP_KEY` — **сгенерировать на сервере**, не переносить локальный:

```bash
cd ~/litoreya/shared && /opt/php/8.2/bin/php -r \
  'echo "base64:".base64_encode(random_bytes(32)),PHP_EOL;'
```
Вставить результат в `APP_KEY=`.

`APP_KEY` — подпись сессионных кук. Локальный ключ переносить нельзя: он лежит в рабочем
дереве разработчика, а публично известный ключ позволяет подделывать сессии.

Права: `chmod 600 ~/litoreya/shared/.env`.

Локальный `backend/.env` не заливать никогда.

### 1.4 Параметры деплоя на своей машине

В корневом `.env` проекта (он в `.gitignore`):

```
DEPLOY_HOST=<пользователь>@<хост>
DEPLOY_PATH=litoreya
DEPLOY_URL=https://<домен>
DEPLOY_PHP=/opt/php/8.2/bin/php
```

`DEPLOY_PHP` — путь к тому же бинарю, под которым работает веб-сервер. `php` из `$PATH`
на shared хостинге часто оказывается другой версии.

Проверить доступ: `ssh $DEPLOY_HOST 'echo ok'` (лучше по ключу, чтобы деплой не спрашивал
пароль на каждом шаге).

### 1.5 Первый релиз
сборка локально
```bash
make release
```
заливка, кеши, миграции, переключение current
```bash
make deploy
```

**Дым-тест в конце первого деплоя не пройдёт — это ожидаемо:** папка домена ещё указывает
на старое содержимое. Переходим к 1.6.

### 1.6 Папка домена → симлинк

Если в 0.3 нашлось поле «корень сайта» в панели — просто укажите там
`litoreya/current/public` и пропустите этот шаг.

```bash
mv ~/<папка-домена> ~/<папка-домена>.backup
ln -s litoreya/current/public ~/<папка-домена>
```

Симлинк **относительный** — абсолютный переживёт переезд хостинга хуже.

Резервную копию не удалять до успешной проверки: если что-то пойдёт не так, вернуть
исходное состояние — это `rm симлинк && mv .backup обратно`.

На хостинге прямо в интерфейсе создал ссылку
litoreya.derin.ru > /var/www/<user_id>/data/litoreya/current/public

### 1.7 Проверка

```bash
make smoke URL=https://<домен>
```

Затем **обязательно вручную в браузере** — curl'ом это не доказывается, потому что Sanctum
в cookie-режиме зависит от связки `Origin`/`Referer` и флагов кук:

регистрация → сохранение recovery-кода → создание записи → перезагрузка вкладки →
разблокировка ключевой фразой → выход → повторный вход.

### 1.8 Редиректы и HTTPS

Канонический адрес и принудительный HTTPS включаются **в панели хостинга**, а не в
`.htaccess`: правило с конкретным доменом в репозитории означало бы редирект на прод при
локальной разработке.

На первом деплое использовать `302`, перевести в `301` только после подтверждения:
постоянный редирект кешируется браузером надолго, и ошибка в целевом адресе лечится только
очисткой кеша у каждого пользователя. HSTS на первом релизе не включать.

## Часть 2. Обновление

### 2.1 Обычный цикл

```bash
make test                      # 91 тест
make prodlike                  # локальная копия раскладки хостинга
make smoke                     # дым-тест по localhost:8081
# ручная проверка в браузере на localhost:8081

make release
make deploy
```

`make deploy` выполняет по порядку, и каждый шаг может остановить деплой **до** того, как
боевой домен посмотрит на новый код:

1. `rsync` в новый каталог `releases/<ts>/` — старый релиз не трогается;
2. проверка, что симлинки `.env` и `storage` разрешаются;
3. `mysqldump` в `shared/backups/<ts>.sql.gz`;
4. `config:cache`, `route:cache`, `event:cache` — **на сервере**, потому что только здесь
   одновременно есть прод-`.env` и правильные абсолютные пути;
5. `migrate --force`;
6. атомарное переключение `current` через `mv -Tf`;
7. дым-тест.

Старые релизы: хранится 5 штук, предыдущий не удаляется сразу — после переключения часть
воркеров ещё около двух минут разрешает путь в старый каталог (realpath cache). Поэтому же
**релизы иммутабельны**: править их на месте нельзя.

### 2.2 Откат

```bash
make rollback              # на предыдущий релиз
make rollback 20260901-120000   # на конкретный
```

Пересобирать кеши не нужно: у каждого релиза свой `bootstrap/cache`, собранный на сервере
с тем же `.env`.

### 2.3 Что откат не вернёт

**Миграции.** `down()` почти никогда не корректен для данных, и `rollback.sh` их не трогает.
Дисциплина — expand/contract: релиз N добавляет колонку и учит код писать в обе, релиз N+1
удаляет старую. Тогда откат N всегда безопасен. Рискованный релиз и разрушительная миграция
не едут в одном деплое. Если миграция была разрушительной — восстанавливать из
`shared/backups/<ts>.sql.gz`.

**Формат payload.** Откат релиза откатывает и фронт. Записи, созданные за окно с новым
`payload_version`, старый клиент не покажет: версия из будущего отвергается намеренно.
Деградация мягкая — дашборд не падает, запись помечается нечитаемой, — но данные исчезнут
из интерфейса до повторного наката.

## Перед Apache стоит nginx

Обнаружено при выкладке PWA. Хостинг отдаёт статику собственным nginx, **не доводя запрос
до Apache**, — а значит `.htaccess` для этих файлов не применяется вовсе:

| Что | Кто отдаёт | Наши заголовки |
|---|---|---|
| `.html`, `.webmanifest` | Apache | применяются |
| `.js`, `.png` и прочая статика | nginx | игнорируются |

Проверяется одной командой — если у ответа нет `x-content-type-options`, значит Apache
его не видел:

```bash
curl -skI https://<домен>/_next/static/chunks/<любой>.js | grep -i 'x-content-type-options'
```

Следствия, которые из репозитория не чинятся:

- **`_next/.htaccess` с `immutable` на год не работает.** Хешированные ассеты приезжают
  с `max-age=86400`. Корректность не страдает — имена хешированные, устареть нечему, — но
  повторные визиты грузят то, что могло лежать в кеше год.
- **Заголовки безопасности не доходят до статики.** `nosniff` и `X-Frame-Options` есть
  у HTML и API, но не у `.js` и картинок.
- **`sw.js` кешируется на сутки.** На обновление приложения не влияет: воркер
  регистрируется с `updateViaCache: "none"`, при котором браузер не спрашивает HTTP-кеш
  для файла воркера. Дым-тест выводит это предупреждением, а не провалом.

Лечится только со стороны хостинга: настройками кеширования статики в панели либо
обращением в поддержку. Если настройки станут доступны — просить `immutable` для
`/_next/static/` и отсутствие кеша для `/sw.js`.

## Диагностика

Симптомы, привязанные к причинам. `make smoke` проверяет всё это автоматически.

| Симптом | Причина |
|---|---|
| `/` отдаёт JSON-404 вместо SPA | `DirectoryIndex` не приехал из `.htaccess` — проверить `AllowOverride All` |
| `/api/health` отдаёт HTML | правило `^api` не отработало: нет `mod_rewrite` или нарушен порядок блоков |
| 500 на всём сайте, включая главную | петля внутренних редиректов: из `.htaccess` убрали блок «существующие файлы и каталоги» |
| Вход не работает, куки нет | `SESSION_SECURE_COOKIE=true` при заходе по `http` |
| «На www не логинится» | домен не перечислен в `SANCTUM_STATEFUL_DOMAINS` |
| 500 и пустой `storage/logs/` | права или квота, а не код: путь до лога тоже берётся из кеша конфигурации |
| `Parse error` на типизированных свойствах | сайт работает под PHP ниже 8.2 — см. 0.1 и 0.3 |
| 403 «Symbolic link not allowed» | `FollowSymLinks` запрещён для домашнего каталога; из репозитория не чинится |
| `ChunkLoadError` у пользователя | открытая вкладка со старым релизом; при штатной работе отсутствующий чанк отдаёт 404 |
| Офлайн не работает, вечное «Загрузка…» | чанки не попали в предзагрузку `sw.js` — это пререндеренная разметка без скриптов; проверяется сборкой |
| `sw.js` приезжает с `max-age=86400` | статику отдаёт nginx мимо Apache, см. ниже. Обновления не ломает: регистрация идёт с `updateViaCache: "none"` |
| PWA не предлагает установку | манифест отдаётся без `Content-Type`: хостинг не знает расширения `.webmanifest`, нужен `AddType` |
