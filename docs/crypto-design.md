# Криптографический дизайн

Детализация раздела 2 из [PLAN.md](./PLAN.md). Документ описывает схему ключей, четыре
операции над ней, реализацию на WebCrypto и известные ограничения.

**Основное свойство системы:** сервер не может расшифровать посты пользователя даже при
полном доступе к базе данных и к своему собственному коду.

---

## 1. Почему не «ключ напрямую из фразы»

Наивная схема: `key = PBKDF2(фраза, salt)`, посты шифруются этим ключом. Она работает ровно
до первого изменения чего-либо и имеет четыре следствия.

**Смена ключевой фразы становится опасной массовой операцией.** Новая фраза даёт новый ключ,
поэтому нужно скачать все посты, расшифровать старым ключом, зашифровать новым и залить
обратно. Операция не атомарна: если вкладка закрылась на середине, часть постов остаётся в
старом ключе, часть в новом, и различить их нечем — признака в данных нет. Корректная
реализация требует серверной транзакции, версионирования и отката. Ради смены фразы.

**Recovery-код невозможен в принципе.** Чтобы код открывал данные, он должен выводить *тот же*
ключ, что и фраза. KDF детерминирован: разные входы дают разные ключи. Остаётся либо хранить
вторую копию всех данных под вторым ключом, либо отказаться от восстановления.

**Смена параметров KDF — снова перешифровка всего.** Поднять итерации с 600k до 1M или перейти
на Argon2id через два года будет стоить той же массовой операции.

**Шаринг между пользователями закрыт навсегда** (см. открытый вопрос №3 в PLAN.md).

## 2. Схема с обёрнутым мастер-ключом

Разделяем два ключа с разными задачами:

```
KEK (key encryption key)   = PBKDF2(фраза, salt, 600k)   — выводится при входе, не хранится
DEK (data encryption key)  = случайные 32 байта          — хранится обёрнутым, не меняется
```

Посты шифруются **DEK'ом**. Ключевая фраза защищает не данные, а DEK. Это стандартная
envelope encryption — так устроены Bitwarden, 1Password, AWS KMS.

### Что лежит на сервере

| Поле | Размер (base64) | Назначение |
|---|---|---|
| `kdf_salt`, `kdf_iterations`, `kdf_algo` | ~24 симв. | параметры повторного вывода KEK |
| `wrapped_dek` + `wrapped_dek_iv` | ~64 + 16 | DEK, обёрнутый ключевой фразой |
| `recovery_dek` + `recovery_dek_iv` + `recovery_salt` | ~64 + 16 + 24 | тот же DEK, обёрнутый recovery-кодом |
| `verifier` + `verifier_iv` | ~40 + 16 | контроль связки «фраза → правильный DEK» |

Смена фразы переписывает 80 байт. Recovery-код — это просто вторая обёртка того же DEK.

## 3. Четыре операции

### Регистрация

```
salt          := random(16)
KEK           := PBKDF2(фраза, salt, 600k, SHA-256)
DEK           := generateKey(AES-GCM 256, extractable: true)
wrapped_dek   := wrapKey(DEK, KEK, iv₁)

recovery_code := random(128 бит) → base32, группами по 4
recovery_salt := random(16)
KEK₂          := PBKDF2(recovery_code, recovery_salt, 600k, SHA-256)
recovery_dek  := wrapKey(DEK, KEK₂, iv₂)

verifier      := AES-GCM(DEK, iv₃, "litoreya-v1")
```

Конверт уходит на сервер вместе с `name/email/password`. Recovery-код показывается один раз,
на сервер не отправляется.

После регистрации DEK нужно «забыть» и заново развернуть как неизвлекаемый — см. §5.2.

### Вход

1. `POST /api/auth/login {email, password}` → сессия + крипто-конверт.
2. Запросить ключевую фразу (отдельный экран разблокировки).
3. `KEK := PBKDF2(фраза, kdf_salt, kdf_iterations)`.
4. `DEK := unwrapKey(wrapped_dek, KEK, extractable: false)` — падает при неверной фразе.
5. Проверить `verifier`.
6. Положить DEK в `KeyVault`.

Ключевая фраза на сервер не уходит ни на одном шаге. Ошибка неверной фразы формируется
локально, без сетевого запроса.

### Смена ключевой фразы

Требует ввода **старой** фразы (см. §5.2 — это не только UX, но и техническая необходимость).

```
DEK        := unwrapKey(wrapped_dek, KEK_old, extractable: true)   // временно извлекаемый
salt_new   := random(16)
KEK_new    := PBKDF2(новая_фраза, salt_new, 600k)
wrapped_new:= wrapKey(DEK, KEK_new, iv_new)
→ PUT /api/auth/keyphrase
```

Посты не читаются и не изменяются. `recovery_dek` остаётся валидным — он обёрнут независимо.

### Восстановление по recovery-коду

Как вход, но KEK выводится из recovery-кода и `recovery_salt`, разворачивается `recovery_dek`.
Сразу после успеха — принудительный экран установки новой ключевой фразы и выдача нового
recovery-кода.

## 4. Реализация на WebCrypto

Вывод KEK:

```js
async function deriveKEK(phrase, salt, iterations = 600_000) {
  const material = await crypto.subtle.importKey(
    'raw',
    new TextEncoder().encode(phrase.normalize('NFKC').trim()),
    'PBKDF2', false, ['deriveKey']
  );
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations, hash: 'SHA-256' },
    material,
    { name: 'AES-GCM', length: 256 },
    false,                            // KEK сам неизвлекаемый
    ['wrapKey', 'unwrapKey']
  );
}
```

Обёртка через `wrapKey`/`unwrapKey`, а не `exportKey` + ручной `encrypt` — тогда сырые байты
DEK не появляются в JS-памяти вообще:

```js
const wrapped = await crypto.subtle.wrapKey('raw', dek, kek, { name: 'AES-GCM', iv });

const dek = await crypto.subtle.unwrapKey(
  'raw', wrapped, kek, { name: 'AES-GCM', iv },
  { name: 'AES-GCM', length: 256 },
  false,                            // ← неизвлекаемый
  ['encrypt', 'decrypt']
);
```

Шифрование поста:

```js
const iv = crypto.getRandomValues(new Uint8Array(12));   // уникальный на каждое сохранение
const ciphertext = await crypto.subtle.encrypt(
  { name: 'AES-GCM', iv }, dek,
  new TextEncoder().encode(JSON.stringify({ title, body, /* поля по типу */ }))
);
```

`extractable: false` в `unwrapKey` — это то, что делает возможным хранение DEK в IndexedDB
(`CryptoKey` структурно клонируем). Такой ключ нельзя прочитать из JS, только использовать:
XSS сможет расшифровать данные, пока жива сессия, но не унесёт ключ на свой сервер и не
получит доступ навсегда.

## 5. Подводные камни

### 5.1 `normalize('NFKC')` обязателен

Ключевая фраза будет на кириллице. Разные платформы и мобильные клавиатуры дают разные
Unicode-нормализации визуально одной и той же строки — байты различаются, PBKDF2 даёт другой
ключ, вход не проходит. Пользователь при этом уверен, что ввёл всё правильно, и воспроизвести
проблему на десктопе не получается.

`.trim()` — по той же причине: автокоррекция мобильных клавиатур охотно добавляет пробел
в конец.

Нормализацию нужно применять **одинаково при регистрации и при входе**, в одной функции.

### 5.2 `wrapKey` требует `extractable: true`

`crypto.subtle.wrapKey` бросает `InvalidAccessError`, если у ключа `extractable === false`.
Отсюда два следствия:

- **Смена фразы** не может работать с DEK'ом, полученным при обычном входе (он неизвлекаемый).
  Придётся переспросить старую фразу и сделать временный unwrap с `extractable: true`.
  Совпадает с правильным UX, но обнаруживается обычно уже в процессе реализации.
- **При регистрации** DEK генерируется извлекаемым (иначе его не обернуть), оборачивается
  дважды — фразой и recovery-кодом, — после чего извлекаемую версию нужно отбросить и заново
  развернуть ключ как неизвлекаемый перед помещением в `KeyVault`.

### 5.3 Verifier проверяет не то, что кажется

Неверная фраза и так уронит `unwrapKey`: `wrapped_dek` — это AES-GCM с тегом аутентичности,
он самопроверяем. Отдельная проверка фразы через verifier избыточна.

Verifier ловит другое — **рассинхрон между обёрткой и данными**: баг при смене фразы записал
новую обёртку от старого DEK, восстановление старого бэкапа строки в БД, частично применённая
миграция. В таких случаях unwrap проходит успешно, но DEK получается не тот, и молча не
расшифровывается ни один пост. Verifier превращает это в понятную ошибку на экране входа
вместо пустого дашборда.

Сравнивать нужно и факт успешной расшифровки, и само значение.

## 6. Ограничения, которые нужно принять осознанно

### Смена фразы ≠ ротация ключа данных

Тот, кто уже получил старую фразу вместе с `wrapped_dek`, извлёк DEK — а DEK не меняется.
Смена фразы защищает от **будущей** компрометации, не от прошлой.

Настоящая ротация DEK — это всё-таки перешифровка всех постов. Её стоит заложить как редкую
административную операцию на случай подтверждённой утечки, но не как обычный пользовательский
сценарий.

### Утечка БД допускает офлайн-перебор фразы

Получив `kdf_salt` и `wrapped_dek`, атакующий перебирает фразу локально, со скоростью,
ограниченной только PBKDF2. 600 000 итераций дают порядка 1–2 секунд на попытку на телефоне,
но GPU-ферма считает в других единицах.

Практический вывод: **ключевая фраза должна быть длинной, а не сложной**. Требования к
спецсимволам добавляют единицы бит энтропии и портят запоминаемость. Вместо них — встроить
в регистрацию генератор diceware-фразы из 5–6 случайных слов и предлагать его по умолчанию.

Стоимость PBKDF2 платит и легитимный пользователь: 1–2 секунды на слабом устройстве при каждой
разблокировке. Это аргумент за auto-lock по таймауту, а не за разблокировку на каждое действие.

### Шаринг отложен, и это не создаёт долга

Шаринг постов между пользователями решено не делать сейчас. Схема это допускает без будущей
массовой перешифровки — при условии, что `payload_version` присутствует с самого первого поста.

Когда шаринг понадобится:

- у пользователя появляется пара ключей: публичный хранится открыто, приватный обёрнут DEK'ом
  (новые колонки, существующие данные не трогаются);
- пост, который шарят, переводится на схему с per-post ключом **в момент шаринга**: клиент
  расшифровывает его текущим DEK, генерирует `K_post`, перешифровывает, оборачивает `K_post`
  своим DEK и публичным ключом получателя. Пост получает `payload_version: 2`;
- нешаренные посты остаются в версии 1 неограниченно долго. Клиент читает обе версии.

Мигрируют только те посты, которые реально шарят, по одному. Это ровно тот сценарий, ради
которого версия payload заложена изначально.

**Единственное, что нельзя сделать задним числом на сервере** — сгенерировать пары ключей
существующим пользователям: приватный ключ должен быть обёрнут DEK'ом, а DEK серверу
недоступен. Значит генерация выполняется на клиенте при первой разблокировке после релиза
шаринга, с записью результата через отдельный эндпоинт. Учесть при планировании той фазы.

### Забытая фраза без recovery-кода = безвозвратная потеря

Это не дефект, а работающее по назначению свойство. Требует явного предупреждения с
подтверждением на экране регистрации и обязательного шага «сохраните recovery-код».

## 7. Что должно быть покрыто тестами

Крипто-модуль пишется первым в фазе 2 и покрывается тестами до того, как появится UI:

- round-trip: `encrypt` → `decrypt` возвращает исходный объект;
- неверная фраза роняет `unwrapKey`, а не возвращает мусор;
- смена фразы: старые посты читаются новой фразой, старая фраза перестаёт работать;
- recovery-код разворачивает тот же DEK, что и фраза;
- verifier ловит подменённый `wrapped_dek`;
- NFKC: фраза в NFC и NFD формах даёт один и тот же KEK;
- IV не повторяется между двумя сохранениями одного поста;
- ни один эндпоинт API не принимает и не возвращает открытый текст поста.
